# ADR-0016: Sync jobs through server-checked RPCs, last writer wins, with a revision cursor

- **Status:** Accepted
- **Date:** 2026-10-01

## Context

Sync is on both paid plans (ADR-0013, revised):

- **Pro:** up to 3 computers.
- **Advanced:** up to 5 devices, including phones through the web board.

ADR-0009 set the shape: a `SyncService` behind a `RemoteJobStore` port, and
`chrome.storage.local` stays the source of truth. Constraints:

- **Local-first:** the board works offline, and sync is a layer on top.
- **The paywall is the server:** a modified extension must not be able to
  sync without a paid plan, or exceed its device limit.
- **Near-zero cost:** Supabase free tier, and no always-on workers.
- **One person's data:** conflicts are rare and come from the same person on
  two devices.

## Decision

### Server (`supabase/migrations/…_sync.sql`)

- **`devices` table:**
  - Holds `id` (generated by the client), `user_id`, `name` (for example
    "Chrome on Windows"), `kind` (`computer` | `web`), `created_at` and
    `last_seen_at`.
  - RLS lets users read and delete their own rows.
  - Rows are added only by `register_device()`, which enforces the limits
    under a per-user advisory lock:
    - Pro: 3 devices, computers only.
    - Advanced: 5 devices of any kind.
    - Free: none.
- **`synced_jobs` table:**
  - Keyed by `(user_id, job_id)`.
  - Each row holds `data jsonb` (the whole Job, null once deleted), a
    `deleted` tombstone flag, `updated_at` (the job's own `updatedAt`) and a
    `revision`, taken from a sequence on every write.
  - The board's settings travel as one more row, `job_id = '@settings'`.
  - The row size is capped. Large descriptions rely on Postgres TOAST
    compression.
- **Reads and writes go only through `security definer` functions:**
  - `push_jobs(device, changes)` and `pull_jobs(device, after, limit)`;
  - both require a registered device and `plan_tier() <> 'free'`;
  - Pro can't push or pull from a `web` device;
  - batches hold up to 500 changes, and a board up to 5,000 rows.
- **Last writer wins:** `push_jobs` upserts only when the incoming
  `updated_at` is newer than the stored one, so a stale device can't
  overwrite a newer edit.

### Client

- **The `sync:state` storage key** (never backed up) holds:
  - `enabled` and `deviceId`;
  - `cursor`, the highest revision pulled;
  - `seen`, mapping each job id to the `updatedAt` last synced;
  - `settingsHash` and `settingsAt`;
  - the last result.
- **A sync run:**
  1. Pull in pages, applying each row unless the local copy is newer.
  2. Push every job whose `updatedAt` differs from `seen`.
  3. Push a tombstone for every id in `seen` that's gone locally.
  4. Push settings (columns, default column, closing alerts; not the theme)
     when their hash changed.
- **Change detection by `seen`** needs no change to how jobs are stored. So
  that reordering a column syncs too, moving a card within its column now
  bumps `updatedAt`.
- **When it runs:**
  - on the 15-minute background alarm;
  - when the board opens or regains focus;
  - a few seconds after a local change.

  A storage lease stops two contexts from syncing at once.

- **Turning sync on** registers the device. At the limit, the account dialog
  lists the devices so one can be removed. Turning sync off removes this
  device, which frees its place, and keeps everything local.
- **When a plan lapses:** sync stops. Local data is untouched, and synced
  data stays on the server until the account is deleted, as the privacy
  policy says.

## Consequences

- **Clock skew:** devices' clocks decide conflicts. That's acceptable for
  one person's devices, and the server never rewrites `updated_at`.
- **Offline deletions:** a job deleted on one device while another edits it
  offline resolves by timestamp, like any other edit.
- **Testing:** pgTAP covers limits, RLS and last-writer-wins, and unit tests
  run the SyncService against an in-memory `RemoteJobStore`.
- **Privacy:** the privacy policy lists device names as stored data.

## Alternatives considered

- **Direct table writes with RLS:** simpler, but RLS can't express a device
  limit or last-writer-wins without triggers that are harder to test.
- **Timestamp cursors:** writes in the same millisecond could be skipped. A
  sequence can't.
- **CRDTs or per-field merging:** more than one person's job board needs,
  and much harder to reason about.
- **A dirty flag on jobs:** it would change the stored Job shape and every
  write path. The `seen` map lives entirely inside sync.
